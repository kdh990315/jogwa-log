# Figma Make 산출물 이식 작업 계획

작성일: 2026-03-24  
작업 브랜치: `feature/figma-migration`  
기준 브랜치: `dev`

## 1. 문서를 먼저 남기는 이유

지금 단계에서 가장 중요한 건 "코드를 그대로 옮길지"가 아니라 "디자인과 기능 결과를 유지하면서 현재 레포 기준에 맞는 구조로 다시 세울지"를 먼저 고정하는 것이다.

이 방식이 최선인 이유는 아래와 같다.

- 현재 Figma Make 산출물은 화면 참고본으로는 가치가 높지만, 구현체 자체는 현재 Next.js 레포 기준과 충돌하는 요소가 많다.
- 이 프로젝트는 `Next.js App Router`, `Server Component 기본`, `pnpm`, 타입 안전성, 이후 `Supabase + RLS` 전제를 지켜야 한다.
- 초기 단계에서 잘못된 구조를 그대로 들여오면 나중에 수정 비용이 가장 크게 커진다.
- 반대로 UI 결과와 인터랙션 요구를 고정한 뒤 내부 구조를 다시 짜면, 화면은 거의 그대로 가져가면서도 이후 기능 확장이 가능해진다.

결론:  
이번 작업의 목표는 `Figma Make 코드 복붙`이 아니라 `동일한 디자인/동작을 현재 레포 구조에 맞게 재구현`하는 것이다.

## 2. 현재 레포 상태

현재 `jogwa-log` 레포는 거의 초기 스캐폴드 상태다.

- `app/page.tsx`에 임시 랜딩 화면만 존재
- `app/layout.tsx`는 기본 메타데이터와 전역 CSS만 연결
- `app/globals.css`는 최소 전역 스타일만 존재
- 아직 Supabase 계층, 공용 UI, 앱 셸, 데이터 계층이 없다
- 브랜치 전략은 `main` / `dev` / `feature/figma-migration`로 정리됨

즉, 지금은 오히려 구조를 깨끗하게 잡고 들어가기 좋은 시점이다.

추가로 현재 라우팅 전제는 아래처럼 고정한다.

- `/`는 소개페이지로 유지
- 실제 제품 화면의 시작점은 `/dashboard`
- 앱 셸이 필요한 화면은 `/dashboard`, `/logs`, `/location-stats`로 분리

## 3. Figma Make 산출물 요약

원본 경로:

- `/mnt/c/Users/User/Desktop/조과로그/낚시 조과 통계 서비스 (1)/src`

현재 확인한 핵심 화면과 기능:

- 대시보드
- 조과 기록 목록
- 포인트별 상세 성과
- 기록하기 모달
- 헤더 / 사이드바 / 모바일 메뉴
- 낚시 타입 토글(바다/민물)
- 차트, 표, 캘린더, KPI 카드
- 라이트/다크 모드 토글

좋은 점:

- 디자인 토큰 의도가 비교적 분명하다
- 카드 밀도, 정보 위계, 낚시 도메인 톤은 괜찮다
- 대시보드 정보 구조가 실제 서비스 초기 MVP에 잘 맞는다
- 바다/민물 분기 UX가 직관적이다

문제점:

- `App.tsx` 하나에 상태와 화면 전환 책임이 과도하게 몰려 있다
- 탭 전환으로 모든 화면을 한 앱 루트에서 처리한다
- mock 데이터가 뷰 내부/근처에 넓게 퍼져 있다
- 생성형 UI 파일이 매우 많이 포함되어 있고 실제 사용 범위는 좁다
- Windows에서는 동작해도 Linux/CI에서는 깨질 import가 있다
- 다수의 UI import가 현재 레포에서 그대로는 성립하지 않는다

## 4. 원본 코드에서 확인된 실제 리스크

이 항목들은 "코드가 마음에 안 든다" 수준이 아니라 실제 이식 시 문제를 만드는 부분들이다.

### 4-1. 단일 클라이언트 루트 구조

`src/App.tsx`가 아래 상태를 한 파일에서 모두 관리한다.

- 활성 탭
- 다크 모드
- 모바일 메뉴
- 기록 모달
- 바다/민물 모드
- 대시보드 패턴 탭

이 구조를 그대로 Next.js `app/page.tsx`에 옮기면 페이지 전체를 `use client`로 올리게 되고, App Router의 장점을 거의 버리게 된다.

### 4-2. 라우트가 아닌 탭 전환 구조

현재는 `dashboard`, `logs`, `location-stats`를 내부 상태로 바꿔 렌더링한다.  
하지만 현재 프로젝트 기준에서는 소개페이지와 앱 화면을 분리해야 하므로 아래처럼 route segment로 나누는 쪽이 맞다.

- `/`
- `/dashboard`
- `/logs`
- `/location-stats`

그래야 소개페이지와 제품 UI의 레이아웃 책임이 섞이지 않고, 로딩, 에러, 메타데이터, URL 공유, 이후 데이터 패칭 책임도 분명해진다.

### 4-3. 케이스 민감도 문제

원본은 아래처럼 import 한다.

- `../ui/Card`
- `../ui/Badge`

하지만 실제 파일명은 아래처럼 소문자다.

- `card.tsx`
- `badge.tsx`

Windows에서는 통과할 수 있지만 Linux 기반 빌드/배포 환경에서는 바로 깨질 수 있다.

### 4-4. 그대로는 쓸 수 없는 import 규격

원본 UI 파일 다수는 아래처럼 버전이 붙은 import를 사용한다.

- `@radix-ui/react-dialog@1.1.6`
- `lucide-react@0.487.0`
- `class-variance-authority@0.7.1`

이건 현재 레포에 바로 들여와서 쓰는 방식으로는 적합하지 않다.  
즉, 생성된 UI 파일 묶음을 통째로 복사하는 접근은 실패 가능성이 높다.

### 4-5. 실제 로직 버그 가능성

캘린더 구현에서 이미 어긋난 지점이 보인다.

- 이벤트 데이터 키는 `"2024-05-01"` 같은 전체 날짜 문자열
- 렌더링에서는 `calendarEvents[day]`처럼 숫자 day로 조회
- 월 계산은 `currentMonth = 4`인데 라벨은 `2024. 04`로 표시

즉, 현재 참고본도 "보여 보이는 것"과 "실제 데이터 연결"이 정확히 맞물린 상태는 아니다.

- `class-variance-authority`

- `vaul`
- `sonner`
- `cmdk`

- `react-resizable-panels`

원칙:

- 실제 사용하는 화면을 다시 구현하는 데 꼭 필요한 패키지만 최소로 도입
- 새 패키지 설치 전에는 반드시 사용자 승인 후 진행

### 7-1. Radix UI / 단순 UI 구현 기준

현재 기준에서 `Radix UI`는 디자인 시스템처럼 통째로 들여오지 않는다.

이렇게 가는 이유:

- 현재 레포는 아직 초기 단계라 의존성을 크게 늘릴수록 구조 고정 비용이 커진다
- Figma Make 산출물의 `@radix-ui/*` 흔적을 통째로 가져오면 클라이언트 경계와 유지보수 비용이 같이 커진다
- 접근성 구현 비용이 큰 primitive만 부분 채택하는 편이 현재 요구사항에 맞다

기본 원칙:

- `Button`, `Card`, `Badge`, 토글 버튼, 탭 버튼 같은 단순 UI는 `React + Tailwind`로 직접 구현
- 위 단순 UI는 처음부터 공용화하지 않고, 재사용성이 높거나 책임 분리가 분명할 때만 분리
- `Dialog`처럼 포커스 트랩, 키보드 접근성, 레이어 관리가 중요한 컴포넌트만 `Radix UI`를 선택적으로 검토
- `Select`는 1차 구현에서는 네이티브 `<select>`를 우선 사용
- `Tooltip`, `Popover`, `Menubar`, `Command`, `Accordion` 등은 초기 이식 범위에서 제외

1차 판단:

- `Radix UI` 없이 최대한 이식 진행
- 기록하기 모달이나 모바일 시트에서 접근성 구현 비용이 높다고 판단되면 `@radix-ui/react-dialog`만 후보로 재검토

정리하면:

- 단순 UI는 직접 구현
- 복잡한 접근성 primitive만 부분 도입
- 공용 컴포넌트 분리는 실제 필요가 생길 때만 수행

## 8. 목표 구조

현재 요구사항에서 가장 맞는 구조는 "소개페이지와 앱 셸을 분리한 서버 중심 route 구조 + 작은 클라이언트 섬"이다.

예상 구조:

- `app/(marketing)/page.tsx`
- `app/(app)/layout.tsx`
- `app/(app)/dashboard/page.tsx`
- `app/(app)/logs/page.tsx`
- `app/(app)/location-stats/page.tsx`
- `app/(app)/loading.tsx`
- `app/(app)/error.tsx`
- `app/globals.css`
- `components/app-shell/*`
- `components/dashboard/*`
- `components/logs/*`
- `components/location-stats/*`
- `components/register/*`
- `lib/mock/*`
- `lib/supabase/*` 또는 이후 도입용 경계

구조를 이렇게 잡는 이유:

- `/` 소개페이지와 실제 앱 화면의 성격이 다르므로 레이아웃을 분리할 수 있다
- 레이아웃 책임을 route segment 기준으로 분리할 수 있다
- 화면별 loading / error / metadata 관리가 쉬워진다
- 서버에서 가능한 데이터 준비를 우선할 수 있다
- 클라이언트 상태는 토글, 모달, 차트 탭 같은 작은 영역으로 제한할 수 있다

## 9. 상태 관리 원칙

이 부분을 먼저 정해야 나중에 덜 무너진다.

- 바다/민물 모드: URL 상태(`searchParams`) 우선 검토
- 대시보드의 패턴 탭: 로컬 UI 상태
- 모바일 메뉴 열림: 로컬 UI 상태
- 기록 모달 열림: 로컬 UI 상태로 시작, 필요 시 route modal로 승격
- 검색/정렬/필터: 공유 필요성이 있으면 URL 상태, 아니면 로컬 상태

현재 기준 추천:

- `mode=sea|freshwater`는 URL 상태
- 대시보드 패턴 탭은 클라이언트 로컬 상태
- 로그 목록 필터는 1차 구현에서는 로컬 상태

이렇게 가는 이유는 "공유되어야 하는 상태"와 "순수 UI 상태"를 섞지 않기 위해서다.

## 10. 데이터 계층 원칙

지금은 Supabase가 붙지 않았기 때문에 1차 이식에서는 mock 기반으로 화면만 먼저 맞추는 것이 맞다.

단, mock이라도 아래 원칙은 유지한다.

- 화면 컴포넌트 내부에 대량 상수 데이터를 두지 않는다
- `lib/mock` 또는 route 근처 데이터 파일로 분리한다
- 타입은 명확히 정의한다
- 나중에 Supabase 응답 타입으로 바꾸기 쉬운 형태를 유지한다

즉, "임시 mock"이어도 나중에 교체 비용이 적은 모양으로 만든다.

## 11. 실제 작업 순서

아래 순서대로 진행한다.

### 1단계. 라우트 분리

- `/`는 소개페이지로 유지
- 앱 화면은 `app/(app)` 아래로 분리
- Figma Make 대시보드의 진입 경로를 `/dashboard`로 고정
- 이후 `logs`, `location-stats`도 앱 영역 route로 정리

목표:

- 랜딩과 제품 화면이 같은 루트에서 섞이지 않도록 초기에 책임을 고정

### 2단계. 디자인 토큰 이식

- 현재 원본 `styles/globals.css`에서 쓸 만한 토큰만 추출
- `app/globals.css`에 현재 레포 스타일 체계로 통합
- 배경, surface, text, line, chart palette, spacing 감각을 먼저 고정

목표:

- 이후 화면을 옮길 때 "먼저 생김새가 무너지지 않도록" 공통 기준을 고정

### 3단계. 앱 셸 구축

- 헤더
- 데스크톱 사이드바
- 모바일 내비게이션
- 공통 컨테이너 폭/패딩/카드 간격

목표:

- 이후 각 화면이 동일한 레이아웃 규칙 위에서 붙도록 만들기

### 4단계. 대시보드 이식

- KPI 카드
- 월별 추이
- 패턴 분석 탭
- 캘린더
- 포인트 요약
- 최근 기록 요약

목표:

- `/dashboard`에 들어왔을 때 보이는 핵심 화면을 원본과 최대한 유사하게 재현

### 5단계. 로그 목록 화면 이식

- 검색
- 필터
- 정렬
- KPI 요약
- 테이블/모바일 카드 대응

목표:

- 화면 밀도와 기능 체감이 큰 영역을 확보

### 6단계. 포인트 상세 화면 이식

- 요약 KPI
- 월별 추세 차트
- 어종 분포
- 최근 로그
- 인사이트 카드

목표:

- 이후 Supabase 설계가 정리되면 서버 액션/route modal 여부 재판단

목표:

## 14. 예상 리스크와 대응

리스크 1:

- Figma Make 디자인과 현재 Next.js 구조 사이에서 구현 디테일 차이가 생길 수 있다

대응:

- 레이아웃, spacing, 색, 카드 비율을 먼저 맞추고 구조는 내부에서 정리한다

리스크 2:

- 원본은 mock 기준이라 실제 서비스 데이터 모델과 1:1 대응이 안 될 수 있다

대응:

- 화면 모델과 DB 모델을 분리해 생각하고, 1차는 뷰 모델로 정리한다

리스크 3:

- 차트 라이브러리나 아이콘 패키지 도입이 필요할 수 있다

대응:

- 실제 필요한 최소 패키지만 후보로 올리고, 설치 전 승인받는다

리스크 4:

- 기록 모달은 UI는 좋지만 실제 저장 플로우는 아직 서비스 설계와 연결되지 않는다

대응:

- 1차는 UI/단계 흐름만 맞추고, 실제 저장은 이후 Supabase 계층 확정 후 연결한다

## 15. 검증 기준

이식 중 기본 검증 기준은 아래다.

- `pnpm lint`
- `pnpm typecheck`
- route 구조/렌더링 경계가 크게 바뀌면 `pnpm build`
- 모바일 폭과 데스크톱 폭에서 레이아웃 점검
- 로딩, 에러, 빈 상태 누락 여부 확인
- 서버/클라이언트 경계가 과도하게 넓어지지 않았는지 확인

## 16. 최종 작업 원칙

이번 이식에서 계속 유지할 원칙은 아래다.

- 디자인은 최대한 그대로 간다
- 구현은 그대로 들고 오지 않는다
- App Router 구조를 지킨다
- `use client`는 최소 범위만 쓴다
- 단순 UI는 `React + Tailwind`로 직접 구현하고, 재사용 근거가 생길 때만 분리한다
- `Radix UI`는 접근성 구현 비용이 큰 primitive에만 선택적으로 사용한다
- 컴포넌트의 props 타입은 컴포넌트 근처에 `interface (컴포넌트이름)Props {}` 형태로 정의한다
- 공용화는 실제 재사용 근거가 있을 때만 한다
- mock은 임시여도 나중에 교체 가능한 구조로 둔다
- 새 패키지는 최소로 도입하고 설치 전 승인받는다
